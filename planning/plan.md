# Build plan for the IT access-request intake

This plan covers `planning/spec.md` R-01–R-114. The implementation record at the end describes the completed original build. Step 12 specifies pending Section 508 acceptance work for that build.

## Choices

- **Runtime:** Python 3.11 or later, standard-library `unittest`, `sqlite3`, `argparse`, hashing and HTTP transport, with `jsonschema` declared in `pyproject.toml` and dependencies locked in `uv.lock`; this fits the supplied Python test harness and keeps deployment small.
- **Interface:** a CLI invoked as `python3 -m intake`, with `run`, `queue`, `resume`, `retry`, `history`, `export` and `accuracy` subcommands; separate invocations can inspect committed results while intake continues, and the same commands support handover and recovery.
- **Tests:** `env -u API_KEY python3 -m unittest discover -s tests -v`, plus the spec’s individual `-k test_rNN_contract` filters; tests use temporary directories/databases, deterministic scripted responses and a blocked real network, so no test or build step needs a real API_KEY.
- **Model provider:** a provider interface with a scripted mock and a configurable OpenAI Responses adapter over an injected HTTPS JSON transport; request model ID, endpoint, request settings and timeout are explicit configuration, with production authentication read only from API_KEY and no credential stored in configuration fingerprints. Verify the exact supported request/response fields against current official provider documentation before implementation, record the chosen model ID/configuration in README and evidence, and test the real adapter entirely through intercepted transport rather than a live call.

The initial supported shared-operation arrangement is multiple CLI processes on one host using one local SQLite database; filesystem/network-share and multi-host database behavior are outside this arrangement and will be documented rather than claimed as tested. SQLite is the authoritative current/history store. Immutable attempts and source revisions are retained separately from current projections, with transactional current-record pointers. Extractions and queue views read the same committed attempt. Export both deliverables from one read snapshot into an immutable generation and expose the generation through one atomic directory reference, so a failed publication cannot expose a half-written generation; document the local-filesystem assumption. An operator reading multiple files across a publication switch must pin one generation. Interrupted workers are recovered through explicit resume with persisted work state and expiring claims; expired workers cannot overwrite a newer claim’s result. Bounded configurable worker concurrency, request timeouts and retry scheduling prevent one slow/rate-limited document from blocking unrelated work; exact tuning is documented as a limit, not a promised throughput.

Only successful, validated extraction results are reusable. Retry explicitly bypasses reuse for the selected document. Configuration identity includes producing provider/model/request settings, prompt and schema versions, and policy version; keep the actual nonsecret configuration alongside the identity. A policy-only change may reroute a retained valid extraction into a new attributed attempt; a failed current attempt is retried explicitly rather than silently replaced by historical success. An unchanged source byte hash distinguishes source identity from changes to producing settings. The latest accepted ingestion revision controls the current pointer; an older in-flight response can remain in history but cannot replace that revision. Order revisions by recorded ingestion sequence, since export timestamps are metadata and no cross-batch source ordering authority is specified.

Business-purpose prose and issue prose have no source-mandated exact wording. Fixtures record supported purpose facts and source quotes, while checking that the actual purpose expresses those facts without unsupported additions. The strict scalar metric compares the 11 non-purpose scalar fields, including nulls; purpose, issues and quote support receive separate checks/reports. This is a declared measurement choice, not a new application acceptance rule or a required accuracy score. The brief’s unspecified performance thresholds and issue vocabulary remain unspecified.

## Test plan

The test plan defines acceptance procedures. Unless a row says otherwise, the provider returns a completed, schema-conforming response saved under `tests/mock_responses/` and the resulting successful record has `error=null`, the original-byte hash and `response_source=mock`. The 12 scalar fields, supporting quotes and issues are checked against an independent source oracle, not against a fixture generated from the output under test. Manual source review is necessary for free-form purpose/issue meaning. Final end-to-end tests in steps 7–11 rerun the earlier contracts through persisted outputs without assigning their test methods to another step.

Case names include the owner step. Each listed `test_rNN_contract` stays in `tests/test_spec_contract.py`; cases may list several methods in the same owner step. Range notation in a case expands to the individual methods stated explicitly in Coverage. Any fixture mentioned here will be authored only during implementation.
